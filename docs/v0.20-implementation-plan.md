# Oxian 0.20 implementation plan

This is the authoritative implementation ledger for the Oxian 0.20 rewrite.
Items are completed in order unless a later item is needed to verify the active
one. A checked item requires implementation plus the evidence named in its
acceptance gate.

## Non-negotiable design rules

- Every native worker connects outbound to the Hypervisor over a versioned WSS
  protocol. Workers do not expose internal HTTP listeners or target URLs.
- HTTP is a workload carried by the worker protocol, not a worker transport.
- Sandbox environments are Oxian workers running a Sandbox-owned workload.
- New components use functional factories and closures. Do not add classes.
- Public runtime APIs use native `Request`, `Response`, `ReadableStream`, and
  `AbortSignal`.
- Providers create, inspect, and terminate compute. They do not transport work
  or determine readiness.
- Readiness comes only from an authenticated, fenced worker session.
- Accepted work is never replayed automatically. A lost accepted operation is
  indeterminate unless its workload explicitly provides durable resumption.
- Work acceptance is two-phase: `work.accepted` reserves capacity without
  invoking the workload; only Hypervisor `work.start`, sent after recording the
  no-replay boundary, authorizes execution.
- Snapshots and checkpoints are workload capabilities, never requirements of the
  generic worker lifecycle.
- Configuration exposes only implemented behavior and is validated at runtime.
- Production claims require tests against the real code path; copied proxy
  snippets and mocked target URLs are not sufficient evidence.

## Ordered work

### 1. Rewrite contract and release line

- [x] Agree on the outbound-WSS worker architecture.
- [x] Start the `0.20.0` package line at `0.20.0-rc.1`; keep the stable `0.20.0`
      tag gated on deployed acceptance.
- [x] Record the implementation, deletion, migration, and verification ledger.
- [x] Keep `0.15.x` behavior isolated from the new architecture; do not add a
      second native worker model to 0.20.

### 2. Worker protocol kernel

- [x] Define package-independent wire version `oxian.worker.v1`.
- [x] Define strict lifecycle frames: hello, welcome, ready, ready
      acknowledgement, heartbeat, drain, drained, shutdown, and protocol error.
- [x] Define strict work frames: open, accepted, start, metadata, data, credit,
      end, cancel, and error.
- [x] Encode bulk data as binary frames without base64.
- [x] Add per-stream sequence validation and credit-based flow control.
- [x] Add correlation, cancellation, connection limits, and frame-size limits.
- [x] Unit-test valid round trips and every malformed/stale frame category.

Acceptance gate:

```bash
deno test tests/protocol
```

The suite must cover interleaved streams, bounded credit, cancellation, invalid
versions, invalid identifiers, invalid ordering, and binary integrity.

### 3. Supervisor and provider primitives

- [x] Implement factory-based worker definition, attempt, and session state.
- [x] Implement fenced lifecycle transitions using attempt ID plus epoch.
- [x] Implement a semantic in-memory worker repository.
- [x] Implement a process-local session registry with replacement fencing.
- [x] Implement a pluggable registration authority with one-time and resume
      capabilities.
- [x] Implement the provider contract and conformance suite.
- [x] Implement local-process and externally-attached providers.
- [x] Ensure provider and session state remain independent.

Acceptance gate:

```bash
deno test --allow-run --allow-read --allow-write \
  tests/supervisor tests/providers
```

The suite must prove concurrent activation safety, stale-epoch rejection,
registration consumption, session replacement, lease expiry, drain, and provider
termination.

### 4. Hypervisor gateway and worker client

- [x] Implement `createHypervisor()` as a runtime-neutral request-admission,
      protocol, and session core.
- [x] Move native WebSocket upgrade and listener ownership into the explicit
      Deno adapter while preserving handshake timeout and strict negotiation.
- [x] Define a callback-based `WorkerWireConnection` for Node, Bun, Cloudflare,
      browser, and future server adapters.
- [x] Implement the outbound worker client with heartbeat, reconnect, resume,
      drain, and shutdown.
- [x] Carry bounded workload-owned bootstrap metadata in `welcome`, run
      pre-ready initialization after durable credential rotation, and return
      bounded workload-owned readiness metadata in `ready`.
- [x] Implement multiplexed work channels with end-to-end backpressure.
- [x] Propagate disconnects and deadlines through `AbortSignal`.
- [x] Route gateway dispatch directly through the authoritative process-local
      session registry and the assigned connection record.
- [x] Fence delayed authenticated gateways with an authority-issued monotonic
      session generation while allowing same-generation lost-welcome retries.
- [x] Bound inbound and outbound transport queues, handshake work, timers, and
      terminal dispatcher retention for indefinitely running processes.

Acceptance gate:

```bash
deno test --allow-net=127.0.0.1 \
  tests/transport tests/hypervisor tests/worker
```

Tests must use real WebSocket connections on ephemeral listeners and cover
multiple concurrent streams, reconnection, stale sockets, slow readers, worker
loss before and after acceptance, ignored request bodies, credential rotation
cut points, proactive drain/reconnect, and graceful shutdown.

- [x] Delete resolvers, materialize, prepare, importer trampolines, resolver

- [x] Delete mutable response state/controllers and compatibility modes.
- [x] Delete interceptors and deprecated shared-file discovery.
- [x] Delete embedded OTLP proxy/collector and manual import-map merging.

### 8. Sandbox local dogfood

- [x] Keep Sandbox imports on exact `jsr:@oxian/oxian-js@0.20.0-rc.1/<subpath>`
      specifiers and use its `deno.json` `links: ["../oxian-js"]` only to
      redirect those imports to the sibling package's public exports during
      local development. Do not map consumers directly to `../oxian-js/src`.
- [x] Add authoritative `check:oxian-local`, `test:oxian-local`, and
      `acceptance:oxian-local` tasks.
- [x] Exercise the production local-process provider against the actual frozen,
      cached fast and environment worker entrypoints through the linked
      package's public exports, not only in-process worker factories.
- [x] Correct the PostgreSQL integration-test environment mismatch: tests read
      `DB_URL_PG`, while current CI supplies `SANDBOX_TEST_DATABASE_URL`.
- [x] Mount the Oxian worker gateway inside the existing Control HTTP server.
- [x] Adapt Sandbox registration persistence to the Oxian registration authority
      and supervisor repository interfaces.
- [x] Run the environment executor through the shared Oxian worker client.
- [x] Convert the inbound-HTTP fast executor into an Oxian WSS worker pool; the
      "all native workers attach outbound" rule has no fast-executor exception.
- [x] Keep terminal, process, preview, workspace, checkpoint, usage, tenancy,
      and credential behavior in the Sandbox workload.
- [x] Add explicit `work.accepted` handling and indeterminate disconnect rules.
- [x] Persist acceptance before `work.start`; never expose a claimed stream to
      Sandbox workload code before start arrives.
- [x] Keep Oxian's worker-session ownership process-local and leave Sandbox's
      durable PostgreSQL relay at the application boundary. Do not publish a
      generic owner/backplane abstraction until a second real consumer proves
      the contract.
- [x] Support a snapshot-free local environment through the attached-computer
      command profile; managed local-process environments retain their durable
      workspace behavior.

Acceptance gate:

- All existing Sandbox unit and integration suites pass.
- The local Control, local environment executor, and a real terminal command run
  through the Oxian WSS path.
- Heartbeats keep the environment ready while the process is alive.
- The real local-process provider passes create, wake, two heartbeats, two
  stateful shell commands, mutation, stop, second wake, and restore.
- Killing the connection after acceptance returns an indeterminate result and
  never reruns the command.
- Process start/stop and preview behavior remain functional.

### 9. Compass attached-computer flow

- [x] Add a Compass-owned device authorization flow using the existing Google
      identity and tenant authorization.
- [x] Add a separately deployable public Oxian Worker Gateway for attached
      computers. Do not make the IAM-protected Sandbox Control service public.
- [x] Have the Worker Gateway consume/verify attachment capabilities through
      authenticated internal Control APIs so only Control accesses PostgreSQL.
- [x] Add Control endpoints for creating and revoking attached worker attempts.
- [x] Deliver a short-lived one-time Oxian registration capability.
- [x] Store only rotating device/resume credentials suitable for a local daemon.
- [x] Make revocation advance a durable session-generation tombstone shared with
      socket ownership, so an exchange completed before logout cannot attach
      after logout completes.
- [x] Package a downloadable worker that uses the same Oxian client and Sandbox
      workload as managed workers.
- [x] Expose online/offline and revocation state. For the command-only MVP,
      stopping the daemon is the local pause and reconnect is the resume; there
      is no separate durable pause/resume state machine.
- [x] Scope local execution to a canonically bound, explicitly selected
      workspace and command-only policy.

Acceptance gate:

- [ ] A user signs in through deployed Compass, authorizes one machine, and runs
      a Sandbox command on that machine.
- [ ] The worker remains connected with heartbeats while the machine is awake.
- [ ] Sleep/network loss reconnects without replaying accepted work.
- [ ] Logout/revocation prevents reconnect.
- [ ] No Compass web-session cookie is used as the daemon credential.

The implementation and local tests are complete. These unchecked items require
the deployed Compass, public gateway, private Control, and downloadable artifact
to be exercised together; local component coverage is not deployed acceptance.

## Progress log

- 2026-07-24: Architecture accepted. The package-independent `oxian.worker.v1`
  kernel, two-phase acceptance boundary, supervisor/provider primitives,
  Hypervisor, reconnecting worker client, HTTP workload, Fetch application
  runtime, router, configuration, and CLI were rebuilt from first principles.
- 2026-07-25: The 0.15 implementation was removed from the 0.20 source tree. The
  package now uses functional factories, process-local exact-session authority,
  bounded streaming/backpressure, real WS/WSS coverage, and no generic durable
  ownership abstraction.
- 2026-07-25: Sandbox local dogfooding completed. Fast and environment workers
  both attach outbound through Oxian, providers own compute lifecycle only, and
  Sandbox retains durable PostgreSQL dispatch, acceptance, settlement, and
  recovery. Real local fast/environment paths cover stateful work, checkpoints,
  reconnect fencing, exact-session shutdown, and no replay after acceptance.
- 2026-07-26: The attached-computer command profile and Compass device flow were
  implemented locally. The downloadable daemon uses the shared Oxian client,
  Google-backed Compass authorization, a public DB-free gateway, heartbeats,
  reconnect, canonical-root confinement, and recoverable revocation. Managed
  checkpoints, process restore, and setup are deliberately outside this MVP.
- 2026-07-26: Local package and downstream verification gates pass. Oxian is
  staged at `0.20.0-rc.1`; Sandbox release imports pin that exact RC, and the
  defined Google Cloud target uses side-by-side `*-v020` resources with retained
  legacy rollback resources. The linked consumer gate now also launches the
  actual frozen, cached fast and environment worker processes through the
  production local provider. Nothing has been published or deployed: the RC,
  frozen release lock, new image digests, zero-delete apply, deployed
  acceptance, rollback drill, and stable release remain explicit external gates.
- 2026-07-27: The immutable `v0.20.0-rc.1` tag reached the publish workflow, but
  its verification job exposed a platform-specific test assumption: Deno may
  inject its internal `node_compat_bin` into `PATH` even when `clearEnv` is
  true. The provider behavior remains unchanged; the test now proves isolation
  with an explicit parent-only sentinel variable. The publish candidate advances
  to `0.20.0-rc.2`.
- 2026-07-27: `0.20.0-rc.2` was published and deployed to isolated `*-v020`
  resources with legacy traffic retained as the rollback target. The first
  deployed acceptance run exposed two pre-dispatch defects: Sandbox passed a
  scalar `WebSocketInit.protocols` value that Deno rejects, and Oxian required a
  canonical Cloud Run Job resource name where the live execution API returns the
  exact short Job ID. Sandbox now passes the protocol as a sequence, and Oxian
  accepts either exact representation while continuing to reject every
  mismatched Job. The cleanup fix advances as `0.20.0-rc.3`; deployed acceptance
  remains an open gate.
- 2026-08-04: `0.20.0-rc.3` and `0.20.0-rc.4` are published. RC4 added the
  direct-stream in-process `WorkerHost` and made it the lightweight local
  default. The RC5 candidate removes Deno server APIs from the package root and
  Hypervisor core, introduces `WorkerWireConnection` plus one-shot
  `Hypervisor.prepare()` admission, preserves the previous listener behavior in
  `/adapters/deno`, and verifies the portable root under Node.
