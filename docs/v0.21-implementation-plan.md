# Oxian 0.21 lifecycle unification and downstream rollout plan

This is the authoritative implementation ledger for the Oxian lifecycle and
transport redesign, followed by its ordered rollout through Ominipg, Sandbox,
Copilotz, and Copilotz Lab. Work is completed in order. A checked item requires
the implementation, cleanup, documentation, and evidence named by its acceptance
gate.

The target Oxian release is `0.21.0-rc.1`. It is a breaking pre-1.0 API release,
but it keeps the compatible `oxian.worker.v1` wire protocol unless an
implementation finding proves that a wire change is unavoidable.

## Non-negotiable architecture decisions

### Roles and vocabulary

- A Hypervisor is always the host of Worker connections and work assignment.
- A Worker is always the client that connects to a Hypervisor and executes
  workloads.
- A Hypervisor publicly declares one or more `transports`; a Worker publicly
  declares one `transport`. In-process and WebSocket are physical transports,
  not different Worker architectures.
- `binding` is reserved for the internal live resource created when the
  Hypervisor activates a transport declaration. It is not a second public
  configuration concept.
- `WorkerHost`, `WorkerClient`, and similar role aliases do not return.
- The local `topic` names an in-process event-fabric namespace. Hypervisors and
  Workers publish and receive the same encoded protocol frames through that
  fabric.
- Event-fabric frames are addressed by logical connection ID and direction. The
  physical transport is bus-like, but work is targeted to one Worker connection
  and is never semantically broadcast for execution.

### Functional public API

Resource-owning primitives may use factories. Data does not require factories.
The public API follows these rules:

- `createHypervisor(...)` and `createWorker(...)` are closure-backed functional
  factories because they own connections, streams, timers, and cancellation.
- Returned values are frozen capability records containing functions, promises,
  streams, and read-only snapshots. They are not classes or mutable service
  objects.
- Plain identities, definitions, credentials, transport declarations, frames,
  and options are plain records accepted directly at validation boundaries.
  Developers should be able to use `satisfies` instead of memorizing `create*`
  wrappers for data.
- Standalone encode, decode, validate, and state-transition functions remain
  appropriate.
- `AbortSignal` owns cancellation. Events or streams expose changing state.
- Do not add `createInProcessTransport()`, `connectToHypervisor()`, or another
  helper whose only purpose is to hide a small declarative record.
- No classes may be introduced in the worker, Hypervisor, lifecycle, protocol,
  binding, or provider implementation.

The intended transport declarations are visible in application code:

```ts
const local = {
  type: "in-process",
  config: { topic: "copilotz" },
} as const;

const websocketHost = {
  type: "websocket",
  config: { path: "/_oxian/workers/connect" },
} as const;

const websocketWorker = {
  type: "websocket",
  config: { url: "wss://workers.example.com/_oxian/workers/connect" },
} as const;
```

Transport-specific physical values live under `config`. Protocol, lifecycle,
workloads, identity, and policy do not.

The intended composition shape is:

```ts
const hypervisor = createHypervisor(
  {
    transports: [local, websocketHost],
    admit,
    assign,
    signal,
  },
  {
    onConnect,
    onAdmit,
    onHandshake,
    onReady,
    onHeartbeat,
    onWorkAssigned,
    onWorkAccepted,
    onStart,
    onComplete,
    onDisconnect,
  },
);

const worker = createWorker(
  {
    id: "copilotz-worker",
    transport: local,
    workloads,
    activate,
    register,
    handshake,
    signal,
  },
  {
    onActivate,
    onRegister,
    onHandshake,
    onReady,
    onWorkAccepted,
    onStart,
    onComplete,
    onDisconnect,
  },
);

await worker.ready;
await worker.closed;
```

Use `transports` on the Hypervisor because it may accept several physical
connection mechanisms concurrently, and singular `transport` on the Worker
because one Worker instance connects through one mechanism. Internally, each
Hypervisor transport declaration produces an active `TransportBinding` that owns
listeners, registrations, logical connections, and cleanup.

Use `register` / `onRegister` consistently. Registration may issue a capability,
but `onIssue` is not a second public synonym.

Worker creation starts its lifecycle. Remove the `run()` plus `whenReady()`
choreography. The Worker capability exposes at least `ready`, `closed`,
`stop(reason?)`, lifecycle events, and a read-only snapshot. The Hypervisor
capability continues to expose natural host operations such as `dispatch`,
`drain`, targeted shutdown, total shutdown, its runtime-adapter ingress, and a
read-only snapshot.

### Lifecycle ownership

Oxian owns protocol ordering. Applications own domain decisions and durable
effects through injected functions and callbacks; they never encode or send
protocol frames themselves.

- `activate` establishes or resumes a logical Worker attempt and returns its
  full fenced identity.
- `register` obtains the initial one-use or resume credential for that identity.
- `admit` replaces the mandatory Oxian authority/repository object pair. It
  validates the Hello identity, consumes or rotates credentials, asserts the
  current attempt, and returns the bounded admission/bootstrap result.
- `handshake` handles Worker-owned durable rotation state after Welcome and
  before readiness. Local ephemeral defaults still execute this lifecycle stage,
  even when they have nothing durable to persist.
- `assign` selects a ready, capable Worker. Oxian provides the normal
  workload/capacity/target implementation and permits an injected function for
  application placement policy.
- `onWorkAssigned` is the host-side durable no-replay gate. It replaces the
  misleading `persistAcceptance` name.
- `onWorkAccepted` on the Worker runs before it acknowledges an offer. The ACK
  is a real `work.accepted` protocol frame in every transport. The Hypervisor's
  callback runs after that ACK is validated.
- `onStart` on the Worker resolves after `work.start` arrives and before the
  workload handler is invoked.
- Ready, heartbeat, completion, and disconnect contexts preserve the complete
  attempt/session fence.

The assignment sequence is fixed:

```text
assign
  -> Hypervisor onWorkAssigned (await durable gate)
  -> work.open
  -> Worker onWorkAccepted
  -> work.accepted
  -> Hypervisor onWorkAccepted
  -> work.start
  -> Worker onStart
  -> workload handler
  -> terminal frame
  -> completion callbacks
```

Lifecycle contexts are immutable and include the stable IDs needed for
idempotency: Worker ID, attempt ID, epoch/session generation, connection ID,
handshake ID where relevant, operation ID, stream ID, lifecycle stage ID,
callback attempt, and `AbortSignal`.

Callbacks that guard a transition are awaited before the state machine advances.
Failure is fail-closed and has one documented retry/reconnect outcome. Callbacks
must be idempotent for their lifecycle stage ID. Disconnect remains a
nonblocking observer so a slow external store cannot retain sockets or prevent
shutdown. The exact blocking status and failure outcome of every callback must
be documented and contract-tested.

Repository and authority remain important domain concepts, but Oxian no longer
forces them into public manager objects. Durable applications can close the
functional `activate`, `register`, `admit`, and lifecycle callbacks over their
own database repositories, APIs, or key services. Oxian may keep internal
ephemeral implementations for local defaults and tests; it must not require
developers to orchestrate `repository.define()`, `repository.activate()`,
`authority.issueRegistration()`, and `authority.exchange()` calls.

### One lifecycle and protocol across transports

There is one Worker lifecycle, one Hypervisor lifecycle, one `oxian.worker.v1`
state machine, one flow-control implementation, and one frame codec. In-process
execution is a transport realization of that architecture, not a shortcut around
it.

Both built-in transports are event-driven. Native WebSocket `open`, `message`,
`close`, and `error` events and local event-fabric publications are normalized
into the same bounded frame-connection contract. Code reuse comes from that
normalization: neither transport binding implements lifecycle transitions.

Every transport executes the same logical sequence:

```text
activate/register
  -> connect
  -> hello/welcome
  -> credential rotation and handshake gate
  -> ready/ready acknowledgement
  -> heartbeat and lease
  -> work open/accepted/start
  -> credit/data/metadata/terminal
  -> drain, shutdown, disconnect, and reconnect policy
```

The default frame representation remains:

- control frames: canonical JSON strings;
- workload data frames: binary `Uint8Array` values;
- media and other large bodies: Web Streams of `Uint8Array` chunks;
- no base64 conversion in the Worker protocol.

The same encoder, decoder, order validator, limits, and credit controller run
for local and WebSocket connections. The in-process path intentionally pays the
small codec/state-machine cost in exchange for one behavior to maintain and
test. It still avoids TCP, TLS, kernel, and network scheduling overhead.

Do not promise zero-copy as a public semantic. Remove avoidable duplicate copies
in the canonical implementation, preserve caller-owned `Uint8Array` behavior,
and let both transports benefit. Consumers continue to use typed arrays and Web
Streams; WebSocket users do not receive a new payload API.

Keep one internal advanced frame-protocol seam so a future measured need can
replace framing, but ship and document only the default protocol in 0.21. Any
future custom frame protocol must declare an ID/version and pass the complete
conformance suite. Do not ship a second optimized local codec in this release.

### Transport declarations and internal bindings

The canonical internal boundary is a bounded logical frame connection:

```ts
type FrameConnection = Readonly<{
  id: string;
  incoming: ReadableStream<string | Uint8Array>;
  send(frame: string | Uint8Array): Promise<void>;
  close(reason?: string): void;
  closed: Promise<ConnectionClose>;
}>;
```

The WebSocket binding adapts native socket events and `send()` calls to this
contract. The in-process binding adapts addressed event-fabric publications to
the same contract. Runtime adapters may receive EventTarget sockets,
server-level callbacks, or other native APIs, but the lifecycle kernel sees only
`FrameConnection`. No transport binding owns lifecycle logic.

The in-process transport's internal binding has these responsibilities:

- a module-realm registry maps an explicit topic to one Hypervisor-hosted event
  fabric;
- duplicate active topic registration fails synchronously;
- a Worker publishes a connect event and the Hypervisor allocates one logical
  connection ID;
- every Hello/Welcome, Ready, heartbeat, work, data, credit, terminal, drain,
  shutdown, and error frame crosses the fabric as an encoded addressed event;
- each event contains the topic, logical connection ID, direction, and
  `string | Uint8Array` frame; only the addressed endpoint processes it;
- per-connection ordering is guaranteed; unrelated logical connections need no
  global ordering;
- bounded per-connection queues and Web Stream backpressure wrap event delivery
  instead of relying on naked synchronous `EventTarget.dispatchEvent()`;
- Hypervisor shutdown unregisters the topic and closes every logical connection;
- Worker stop/hot reload removes listeners and references;
- multiple Copilotz/Ominipg instances are isolated by distinct topics; and
- the transport is same-realm only. Cross-realm support is a future MessagePort
  transport, not an implicit promise of this one.

The fabric is transport, not ambient authority: possession of a topic still
enters the same activation, registration, admission, handshake, fencing, and
lease lifecycle. Although publication is bus-like internally, assignment and
execution remain exact-connection operations.

For WebSocket transports:

- Hypervisor config is listener-oriented (`config.path`);
- Worker config is connection-oriented (`config.url` and socket-specific
  options);
- the runtime-neutral Hypervisor exposes upgrade/Fetch ingress;
- Deno, Node, Bun, Cloudflare, and browser/runtime adapters own native listener
  or socket construction; and
- WSS is the production default across trust/process boundaries.

A Hypervisor may declare in-process and WebSocket transports simultaneously. The
same Worker declaration changes only `transport` and lifecycle integrations when
moved across that boundary.
